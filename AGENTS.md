# Repository Rules

These machines deploy secrets via sops-nix (age-encrypted) and 1Password.
Tool output and transcripts are shared surfaces: anything an agent prints
can end up in chat, logs, commits, or CI. The rules below are absolute.

## Secret material handling

### Never execute

Primary rule: except for the explicitly allowlisted verification
commands below, never execute ANY command that reveals or emits the
secret value / body from the paths below into provider-visible output
(tool stdout/stderr, transcript) or into any new plaintext artifact (file,
redirect, pipe consumer). This includes (but is not limited to) `cat`,
`less`, `more`, `head`, `tail`, `grep`, `sed`, `awk`, `perl`, `python`,
`strings`, `xxd`, `base64`, and `od` — an enumeration bypass via an
unlisted tool is still a violation. Secret paths:

- `~/.config/sops/age/keys.txt` — age private key
- `~/.ssh/id_ed25519_github` or any other SSH private key body
- anything under `~/.config/sops-nix/` — decrypted secrets
- `~/.config/zsh/secrets.env`, `~/.config/opencode/opencode.json` —
  sops templates carrying API keys / bearer tokens

Likewise never run:

- `sops --decrypt` / `sops -d` (including output to stdout or a file)
  and `sops edit` on `secrets/secrets.yaml` or `secrets/github_id_ed25519`
- `op read 'op://...'` and `op item get` on secret items — 1Password
  values are restored interactively by the user, never by an agent
- `git add` / commit of plaintext secret material; `secrets/` may contain
  only sops-encrypted files

Also never quote or paste output of the above into replies, issues, PR
descriptions, commit messages, or logs — including "just to confirm".

### Safe verification commands (sole permitted exceptions)

These are the only permitted readers of the paths above — for metadata
and public-key derivation only, never the secret body:

- `ls -l <path>` / `ls -lL <symlink>` — existence, permissions (expect
  mode 0600), and symlink targets, without file contents
- `file ~/.ssh/id_ed25519_github` — format check without contents
- `nix run nixpkgs#age-keygen -- -y ~/.config/sops/age/keys.txt` —
  public recipient only; compare against the age key in `.sops.yaml`
- `ssh-keygen -lf ~/.ssh/id_ed25519_github.pub` — public fingerprint
  (`-lf` for public key files; do not combine with `-y`, whose behavior
  in that combination is version-dependent)

Logs (e.g. `~/Library/Logs/SopsNix/stderr`): the provider-visible output
of the command — what the tool returns and the transcript captures — MUST
contain only sanitized lines. Do not build this by piping raw matched
lines between stages (a malformed redaction stage would surface them
verbatim). Use one process that filters, redacts, and only then prints:

    perl -ne 'next unless /decrypt|error|failed/i; s{[A-Za-z0-9+/=_-]{20,}}{[REDACTED]}g; print' \
      ~/Library/Logs/SopsNix/stderr

If a task seems to require reading secret material, stop and ask the
user instead of working around these rules.

### Asynchronous secret deployment on macOS

Secrets are not placed during switch activation. At the end of
activation, a LaunchAgent (`org.nix-community.home.sops-nix`, bootstrapped
via `launchctl bootstrap`, RunAtLoad, asynchronous) runs
`sops-install-secrets` afterwards. A placement failure therefore never
fails the switch: the exit code stays 0 ("switch succeeded, key missing")
and failure details appear only in `~/Library/Logs/SopsNix/stderr` — read
that log only through the sanitizing filter shown above. After switching,
verify placement with `ls -l ~/.ssh/id_ed25519_github` instead of trusting
the exit code.

## Tool management (mise)

Stable CLIs are nix packages; language runtimes and fast-moving agent CLIs
(claude-code, codex, oh-my-pi, pi, headroom-ai, apm) are managed by mise.
The mise config itself is generated by nix (`modules/home/mise.nix`), so
never run `mise use -g`. Apply tool changes by editing the module and
switching.

## Applying changes

Apply changes with the switch commands in README.md. Additional rules:

- The Git flake excludes untracked files: `git add` new files before
  switching, otherwise the switch fails.

## Agent skills (APM)

Skill bodies are never committed to this repository — only the manifest
`config/agent-skills/apm.yml` and the lockfile `config/agent-skills/apm.lock.yaml`
are tracked. Home Manager places both under `~/.config/agent-skills/`; every
switch runs the `skills-sync` activation, which executes `agent-skills-sync`
to install them into the active APM environment (`~/.apm/`).

- Run APM from the home directory so project-local mise configs cannot
  pin different tool versions (see commands below).
- Until the skills sync triggered by a switch has completed, do not run
  any other APM operations.

### Updating skills

```sh
cd "$HOME"
# Preview or update user-scope dependencies.
mise exec -- apm update --global --dry-run
mise exec -- apm update --global

# Or update a single skill by fully specifying its manifest source.
mise exec -- apm update --global github/awesome-copilot/skills/git-commit
```

Import the changed manifest and lockfile into the repo and review the diff:

```sh
cp "$HOME/.apm/apm.yml" ~/dotfiles/config/agent-skills/apm.yml
cp "$HOME/.apm/apm.lock.yaml" ~/dotfiles/config/agent-skills/apm.lock.yaml
cd ~/dotfiles && darwin-rebuild switch --flake .#helium
git diff -- config/agent-skills
# Commit & push the reviewed changes as usual.
```

- Always import updates before switching: with un-imported changes in the
  active APM definitions, the sync refuses to overwrite.
- Never hand-edit the resolved commits in the lockfile.
- Propagate to other machines by switching them to the same commit.

### Adding and removing skills

Specify the target skill's directory as the source, not a plugin or an
entire repository collection:

```sh
cd "$HOME"
mise exec -- apm install --global --only apm owner/repository/path/to/skill
mise exec -- apm uninstall --global owner/repository/path/to/skill
```

Import both APM definition files into the repo, review the diff, switch,
and commit & push — the same flow as updates. On machines receiving the
change, the sync adapter removes only files that were previously managed
and unchanged locally: locally modified retired files are kept and
reported, and unmanaged files are protected.
